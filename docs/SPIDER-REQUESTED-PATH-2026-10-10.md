# مسیر درخواستی Spider؛ شکست مسیر مستقیم و بازنشستگی تست — ۲۰۲۶-۱۰-۱۰

## حرف آخر کاربر
«بدون وپن باز نشد … همون معماری اسپایدر رو می‌خوام … دقیقا مثل همون».
اسکرین‌شات 18:41:02 گوشی: HTTPS ناموفق، WebSocket ناموفق، خروجی سرور نامشخص. این نتیجهٔ واقعی خط کاربر است و جایگزین/ابطال‌شونده با تست موفق sandbox نیست.

## اصلاح مسیر
تست ساخته‌شده فقط گوشی → Railway بود، نه معماری CDN ایرانیِ آموزش. نباید آن را جای اجرای هدف کاربر پیش برد یا از شکست آن نتیجه گرفت که مسیر CDN ایرانی هم ناممکن است.
API در زمان بازنشستگی، دیپلوی را SLEEPING نشان داد؛ بنابراین علت قطعی خطا (فیلترینگ/مسیر/بیدارشدن سرویس/علت دیگر) از این شواهد به تنهایی قابل تعیین نیست. حکم عملی: مسیر مستقیم روی خط کاربر تأیید نشده و ناموفق گزارش شده است.

## کار واقعاً انجام‌شده
- نتیجه و عکس کاربر در وضعیت خصوصی ثبت شد؛ هیچ نود Railway به اشتراک Omni اضافه نشده بود و اضافه نشد.
- deploymentStop برای حالت SLEEPING خطای not stoppable داد؛ به‌اشتباه «متوقف شد» ثبت نشد.
- deploymentRemove سپس true داد؛ query بعدی latestDeployment=null بود. دیپلوی برنامهٔ تست مستقیم جمع شد؛ پروژه/تنظیمات برای سابقه باقی است.
- deploy.py با retired=true از ایجاد دوبارهٔ تست مستقیم جلوگیری می‌کند.
- هیچ خرید/کارت/ارتقای پولی انجام نشد؛ سرویس‌های قبلی Cloudflare و اشتراک‌ها دست‌نخورده‌اند.

## معماری‌ای که کاربر می‌خواهد
V2Box → لبهٔ قابل‌دسترسی CDN ایرانی برای دامنه/زیردامنهٔ تحت کنترل کاربر → origin خارجیِ اجرای خود SpiderPanel → اینترنت.
Railway نقش origin را دارد، نه نقطهٔ اتصال مستقیم لازم برای گوشی. اتصال مستقیم به hostname ریلوی معیار این معماری نیست.

### انطباق با کد اصلی بررسی‌شده
- README اصلی دو استقرار VPS و Railway را معرفی می‌کند؛ Dockerfile و railway.toml اصلی روی 0.0.0.0:8080 اجرا می‌شوند.
- ورودی مدیریت‌شدهٔ TLS+WS در main.py توسط relay خود FastAPI انجام می‌شود؛ نباید آن را با REALITY مستقیم یا صرفاً یک Xray REALITY جایگزین کرد.
- SETTINGS.domain/public domain باید نام frontend واقعیِ تحت کنترل کاربر باشد. در صورت استقرار پشت CDN، SPIDER_PANEL_PUBLIC_DOMAIN/SPIDER_PANEL_PUBLIC_URL و تنظیم domain باید با آن هماهنگ شوند؛ hostname کشف‌شدهٔ Railway نباید بی‌دلیل جای frontend را در URI بگیرد.
- Address قابل تغییر است؛ در generate_user_config برای default TLS+WS، tls_host=panel_domain می‌ماند. Host و SNI واقعی متعلق به همان دامنه‌اند.
- default_tls_ws_spoof_enabled / _spoof_payload خروجی جداگانهٔ snispoofing با active، fakeSni، spoofIp و targetPort می‌دهد؛ در کد برای V2Box ذکر شده و به REALITY اعمال نمی‌شود. مقادیر پیش‌فرض نمونه نباید به‌عنوان مسیر واقعی منتشر شوند.
- در CDN باید HTTPS origin/Host/SNI با origin hostname ریلوی سازگار باشد و WebSocket و مسیر تولیدی خود Spider بدون rewrite/challenge مخرب عبور کند. این تنظیمات هنوز روی CDN اجرا نشده‌اند.
- همان مسیر نهایی باید با خود V2Box و ترافیک واقعی روی خط کاربر آزموده شود؛ echo موفق کافی نیست و هیچ تضمین نت ملی داده نمی‌شود.

## ورودی بعدی لازم، نه خرید VPS
با دسترسی موجود، نام دامنه/زیردامنهٔ تحت کنترل DNS کاربر و CDN ایرانیِ متصل به آن مشخص نیست. لیست zones حساب Cloudflare متصل موفق بود ولی صفر مورد برگرداند؛ این اثبات نمی‌کند کاربر در حساب یا رجیسترار دیگری دامنه ندارد. جست‌وجوی محدود نام فایل‌های Arvan/آروان در Drive نیز صفر بود و کلید CDN ایرانی در متغیرهای فعلی یافت نشد.
قدم انسانی بعدی: نام دامنهٔ تحت کنترل خود کاربر و نام CDN متصل به آن را دریافت کنیم. اگر ندارد، بدون دستور تازه خریدی انجام ندهیم؛ «رایگان اول، پولی بعد» پابرجاست. دامنهٔ عمومی اسنپ به جای مالکیت DNS/تنظیم CDN کاربر نیست.

## وضعیت واقعیِ نصب
خود SpiderPanel روی Railway هنوز نصب نشده است. CDN ایرانی وصل نشده و مسیر موردنظر کاربر هنوز ساخته/آزموده نشده است. محدودیت فعلی AUP ریلوی دربارهٔ میزبانی پروکسی، که قبلاً توضیح داده شد، همچنان حل نشده؛ API token صرفاً دسترسی فنی است، نه تأیید این کاربرد از طرف ارائه‌دهنده. گزارش یا UI نباید نتیجهٔ موفق ساخت کل زنجیره را ادعا کند.
