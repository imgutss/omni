# Omni Central rev154 — WARP registration repair candidate

Date: 2026-10-30  
Target: `https://omni.nguts.workers.dev`  
Base / immediate rollback: **rev153**  
Older preserved rollback: **rev152**

## Status

This document describes the tested **rev154 candidate**. It is not, by itself, evidence that the public central Worker has changed. Final deployment evidence is recorded separately in `REV154_LIVE_2026-10-30.md` after a successful deployed readback and authenticated smoke test.

The published native Android v0.5.0 line is unchanged.

## Root cause

rev153 still registered devices with the obsolete Cloudflare WARP API/version fingerprint. Cloudflare could answer that registration with HTTP 429, which rev153 relayed as HTTP 502. The panel also had implicit registration triggers and two generation handlers, so opening/selecting parts of WARP Studio could cause unexpected registration attempts and repeated transient error toasts.

A 429 was therefore not evidence of a D1 outage, and simply rewording the toast would not repair registration.

## Repair

- Uses the current registration contract: `v0a5641`, `CF-Client-Version: a-6.38.9-5641`, and the Android 6.38.9 user agent.
- Generates a fresh X25519 keypair in the Worker and validates the complete upstream account before persistence.
- Does not retry the non-idempotent registration POST. A 429 remains a 429 with `warp_rate_limited` and a parsed `Retry-After` value.
- Rejects malformed/incomplete upstream replies and does not save them as accounts.
- Coalesces concurrent generation through a short D1 lease. Callers wait for the committed account instead of registering more devices.
- Reuses a valid existing account for ordinary generation. Only the explicit “fresh key” action rotates it.
- Rotation preserves the endpoint and AWG fields, protects against stale settings writes, and keeps the previous account if registration or persistence fails.
- A newly registered device is deleted when saving its account fails, preventing an orphaned Cloudflare registration.
- Registration bearer tokens remain server-side and are removed from status/settings responses. Private keys are not logged.
- The browser has one generation fetch site and one single-flight flow. Endpoint selection and opening WARP Studio no longer register a device implicitly.
- Errors remain visible after the toast disappears; successful status/account responses replace stale browser state.

## Deployment and rollback procedure

`deploy_v94_central.js` requires `CF_TOKEN` in the process environment. It writes no credential to disk.

Preflight requires all of the following to match rev153 exactly:

- public `/api/version` revision and panel build;
- `releases/current` and the rev153 rollback KV entry;
- local rev153/rev154 source hashes;
- central D1/KV bindings, secrets, compatibility settings, and the `OmniEgress2` Durable Object export.

The script then:

1. adds `releases/v60.1-rev154-warp-registration` without deleting earlier releases;
2. uploads rev154 while retaining existing bindings/secrets and SQLite Durable Object storage;
3. reads back the deployed revision and panel;
4. runs the existing central smoke checks and WARP authorization/wiring checks;
5. creates a random ten-minute admin session through D1 solely for verification, and deletes it in `finally`;
6. tests authenticated generation/reuse without forcing rotation of a valid existing account;
7. compares the returned account with central D1 without printing private keys or registration tokens;
8. sets `releases/current` to rev154 only after every check passes.

Any failure after upload triggers rev153 restoration and a rev153 readback. rev152 and rev153 sources remain preserved.
